# 系统架构设计说明

## 1. 设计目标

评测系统需要满足以下核心约束：

| 约束 | 描述 |
|------|------|
| **防作弊** | 参赛队不能提前解密考题，不能提前查询真值 |
| **实时性** | 参赛算法在线处理，每题限时（默认 30 分钟） |
| **公平性** | 评分独立于参赛软件，在裁判端计算 |
| **鲁棒性** | 单点故障不影响其他参赛队，异常自动重试 |
| **可审计** | 所有通信留日志，赛后可复现判决 |

### 2.2 各组件职责

| 组件 | 语言 | 进程数 | 主要职责 |
|------|------|--------|----------|
| 比赛服务器 | — | 1 | 赛事管理、分数汇总、排行 |
| 裁判客户端 | Java | 每队 1 个 | **通信中枢**：转发考题指令、下发 token、收集答案 |
| 评判应用 | C++/Qt | 每队 1 个 | **评分核心**：读 GT、比对答案、算分 |
| 参赛软件 | 各队自研 | 每队 1 个 | 接收加密数据 → 解密 → 算法推理 → 输出答案 |

## 3. 关键设计决策

### 3.1 为什么裁判客户端是 Java？

- 团队既有 Java 工程经验
- 需要处理 5 个端口的并发 Socket，Java 的 `ExecutorService` 与 `BlockingQueue` 提供成熟方案
- 与主办方原有系统（Java 系）生态一致

### 3.2 为什么评判应用是 C++？

- 需要**实时处理激光雷达点云**（LiDAR 一帧约 32000 点，10Hz）
- OpenCV 与 PCL 等点云库主要为 C++ 生态
- Linux 部署，避免 Windows 环境下的路径/编码问题

### 3.3 为什么拆成 Java 客户端 + C++ 评判应用两个进程？

**职责隔离**：
- Java 客户端专注**通信编排**，无重计算
- C++ 应用专注**算法计算**，不需要处理网络

**开发解耦**：
- 客户端由软件组维护
- 评判应用由算法组维护

**容错**：
- 一方崩溃另一方不退出，可重启对应进程恢复

**代价**：跨进程通信协议需要设计（本项目通过 TCP loopback 6002/6003 端口完成）

## 4. 数据流

### 4.1 赛前准备

```
原始考题数据
    ├── 相机图像 (JPG, 不加密)
    ├── 传感器 CSV (加密) ────┐
    ├── LiDAR PCAP (加密)  ───┤
    ├── URG LMS (加密)     ───┤──► 加密工具 (Python)
    └── Ground Truth CSV ─────┘         │
                                        ▼

                                  + token.csv (裁判保留)
```

### 4.2 比赛中

```
Server ──考题路径──► 裁判客户端 ──加载考题──► 参赛软件
                                    ▲
                                    │ 每 100ms
                                    │
                              token.csv 读取
                                    │
                                    ▼

                                    │
                                    ▼

                                    │
                                    ▼

                                    │
                                    ▼

```

## 5. 容错与超时

| 场景 | 处理 |
|------|------|
| 参赛软件 5s 无答案 | 心跳计数 +1，3 次后判定离线 |
| Token 下发失败 | 立即重试 1 次，仍失败则记录异常 timestamp |
| 服务器指令超时 | 保留最后一条有效指令，等待恢复 |
| 参赛软件崩溃 | 裁判客户端重启对应子进程，从断点 timestamp 继续 |

## 6. 已知架构缺陷

1. **单点故障**：每队的裁判客户端崩溃 = 该队中断
2. **消息丢失**：TCP 本身可靠，但应用层无 ACK
3. **水平扩展困难**：Java Socket 单机承载有限
4. **中文路径**：Java Properties 加载含中文路径时可能失败（历史踩坑）

## 7. 演进方向（如果重做）

- 用 **Netty** 替代原生 Socket
- 引入 **Kafka** 解耦通信层与评分层
- 使用 **gRPC + Protobuf** 定义标准化协议
- 排行榜使用 **Redis Sorted Set**
- 数据分发使用 **CDN + 对象存储**（OSS/S3）
